# 核心文件结构与接力约定

首次为项目创建核心文件、或要调整项目结构时读本文件。文中结构均为**要填实际内容的说明**：没有信息的章节写一行"待确认：…"即可，不要留空表格、不要写占位文字、不要虚构细节。

## AGENTS.md（项目入口）

按序包含：

1. 一句话项目定位 + 当前阶段（指向 STATE.md）。
2. 阅读顺序：AGENTS.md → STATE.md → 按需 PROJECT.md / 专题文件。
3. 文件职责表（三核心文件 + 已有的专题文件）。
4. 接力规则——这是接棒者无需安装任何技能也能正确维护的最低规则集：
   - 任务状态只有五种：**待做 / 进行中 / 待验收 / 完成 / 阻塞**。
   - 待验收 → 完成必须附证据：产物路径 + 验证命令或输出，或用户确认。"已生成"≠"已完成验收"。
   - 下一步四要素：**行动、所需输入、预期产物、完成条件**。
   - 外部动作查到回执才算完成；结果不明先查回执，不重复执行。
   - 更新时机：完成可验收步骤 / 关键决定变化 / 遇阻塞 / 交接前 / 中断恢复核对后——不必等用户要求"保存进度"。
   - 记录与实际冲突：以实际为准，先修正记录再继续。
5. 授权指引：哪些可直接做，哪些必须先问（细则放 PROJECT.md「约束与授权」，此处一句话 + 链接）。

## PROJECT.md（项目定义）

章节：

1. **目标与背景**——最终产物是什么，给谁用。用户陈述标【事实】，推断标【假设】。
2. **范围**——明确写"做什么"和"不做什么"。不做清单和做清单同样重要。
3. **交付物与验收标准**——每项交付物配一条可检验的验收方法（命令、输出、文件内容、用户确认），避免"效果良好"这类无法核对的表述。
4. **约束与授权**——技术、时间、资源约束；哪些动作可直接执行、哪些必须先经用户确认。
5. **阶段方案**——每个阶段有产出与验收方法。阶段数量按项目规模：小项目 2–3 个即可，不为凑结构造阶段。
6. **关键决定记录**——决定、理由、日期。决定变了追加新条目，不删旧条目。
7. **待确认清单**——启动时没答上的问题，集中放在这里。

## STATE.md（当前状态）

章节：

1. **当前阶段与整体进度**（一两行）。
2. **任务表**：任务 / 状态 / 产物或证据 / 备注。状态严格用五态，不自创（想写"基本完成"时，写"待验收 + 缺什么"）。
3. **阻塞**：阻塞点、已尝试的办法、需要谁决定。
4. **未决问题**：不影响当前行动的问题放这里，不打断工作。
5. **下一步**：恰好一个，四要素齐全。反例："继续完善文档"。正例：
   > 行动：运行 `python -m unittest discover` 并保存输出。
   > 所需输入：仓库根目录（含 tests/）。
   > 预期产物：测试通过输出（作为 T2 验收证据）。
   > 完成条件：全部用例通过，T2 更新为完成并附证据。
6. **归档链接**：较长历史放 `archive-*.md` 或专题文件，从这里链接。

## 专题文件

- **新增条件**：某类信息反复更新，塞进核心文件会让状态文件臃肿（如科研的实验记录、学习的练习验收、软件的架构说明）。
- **要求**：文件头一句话说明用途；从 AGENTS.md 职责表和/或 STATE.md 链接进入；命名表达用途（`LOG-experiments.md`、`ARCHITECTURE.md`）。
- **禁止**：预建空文件；把"当前状态"写进专题文件（当前状态只在 STATE.md）。

## 已有项目的合并规则

- **已有 AGENTS.md**：局部合并。原文保留，追加"项目接力"章节（阅读顺序、职责表、更新规则）；不得删除或改写原有规则。
- **已有兼容入口/记录**（NOTES.md、TODO.md 等）：优先复用改造并在 AGENTS.md 建立链接，不复制正文、不维护两套事实；确认无用才放弃。
- 改动前核对原文件内容，合并后向用户说明改了什么。

## 措辞与状态纪律

- 证据写具体路径、命令、输出摘要；不写"应该没问题""大概率完成"。
- 外部动作写执行时间与回执位置（链接、日志路径、回执文件）；恢复时回执未确认，先查回执再决定是否重做。
- 中断/异常恢复：先核对文件与外部状态，再改记录、再继续。
