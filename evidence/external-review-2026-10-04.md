## 需要修正的问题

### 1. P1：完成门槛允许“命令”充当已验证结果，冲突处理又过度相信现有产物

位置：`references/file-conventions.md:14`、`SKILL.md:45`；该规则会复制进生成项目的入口。

现有规则允许以“产物路径 + 验证命令或输出”把任务从待验收改为完成，并要求冲突时“以实际为准”，称“实际产物不会撒谎”。验证命令只是验证方法，不证明执行成功；现有文件也可能是旧版、部分生成或已被修改的产物。

反例：状态引用旧版测试通过记录，而报告或代码已改变；接棒者看到文件和验证命令，却没有当前版本的执行结果，仍可能满足字面上的“附证据”要求。当前流程没有要求检查证据是否仍适用于现有输入与产物。仅查看内容也不能替代项目所要求的运行验证。

最小修正：完成必须有实际执行结果或明确用户验收，并能对应当前输入、产物和验收条件；适用时记录版本、日期或摘要，无需强制给每个文件计算哈希。证据缺失、过期或冲突时保持待验收，先核对或重验受影响部分。把“实际产物不会撒谎”改为“实际产物是核验对象，不自动等于正确结果”。

证据层级：源文件可直接确认规则缺口；本次正常接力案例没有触发错误完成，不能把该反例表述为已经实测失败。

### 2. P2：已有少量记录时，没有可执行的复用和补齐路径

位置：`SKILL.md:24`、`SKILL.md:44`、`references/file-conventions.md:56-57`。

启动规则把存在其他规则或笔记的项目直接转入恢复；恢复规则却固定读取 `STATE.md`，而合并规则又允许复用 `NOTES.md`、`TODO.md` 等现有记录。对“只有原生 AGENTS.md 和 TODO.md”的项目，这几条无法给出一致的读取、写入目标。接手者只能自行决定缺失文件怎么处理，容易卡住或产生重复的状态来源。用户仅要求补搭框架时，也不应因为目录里有笔记就进入执行业务的分支。

最小修正：区分空项目、完整接力记录、部分或旧记录。部分记录先检查职责是否齐全，按原有事实来源补齐并在入口写清实际路径映射；恢复和维护均服从该映射。是否执行下一步由当前用户请求决定，而非由文件存在与否决定。

证据层级：静态流程缺口；本次没有把部分旧记录迁移作为运行验证。

### 3. P2：把用户陈述直接标成事实，会在接力中固化未经验证的前提

位置：`SKILL.md:26`、`references/file-conventions.md:25`。

“用户明确说的是事实”混淆了用户要求与客观事实。例如用户说“我觉得方法 B 一定更有效”或“听说这个接口免费”，不能因为来自用户就被写成已证实事实。新会话看不到原始语气，可能据此选方案、跳过实验或制定预算。

最小修正：分别记录用户目标/选择、用户提供但未核实的信息、已验证事实和假设，保留来源与确定程度。在形成阶段方案前，根据最终目标、已验证事实、硬约束和待验证假设推导必要步骤；用户提出的实现办法若不是硬约束，应作为候选方案。这也补足当前只做信息分类、没有明确从基本条件推导路径的第一性原理环节。

证据层级：规则本身可直接确认；本次启动输入没有包含诱导性的错误说法，因此不声称已复现错误判断。

### 4. P2：README 的既有实测结论没有可追溯证据

位置：`README.md:65-70`。

README 声称科研和软件两种框架、无历史会话接力、记录与实际冲突处理、外部回执核对及零改写合并均已验证。当前仓库仅有四个说明文件，这些结论未链接输入、产物、运行记录或对应版本。本次无法据此复查。证据可能保存在别处；没有随包提供证据不等于可以断言测试从未发生。

最小修正：补充可访问的验证记录，标明输入、版本、过程、输出和限制；无法找到证据的条目改为“历史自述，待核对”或“待验证”。本报告只能支持下面明确执行的范围，不能补证 README 中其余场景。
